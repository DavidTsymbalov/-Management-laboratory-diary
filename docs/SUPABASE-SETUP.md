Проект: `pnpanexhudlalavcevck`. Адрес и публичный ключ уже заданы в `src/lib/supabase.ts`. Secret/service_role key нельзя добавлять в клиент, GitHub или переменные `NEXT_PUBLIC_*`.

## 1. Таблицы

Откройте [SQL Editor](https://supabase.com/dashboard/project/pnpanexhudlalavcevck/sql/new), создайте запрос, вставьте **весь** файл `supabase/migrations/202611030001_classroom.sql` и нажмите **Run**. Запрос выполняется один раз в новом пустом проекте. После успеха появятся таблицы `teachers`, `students`, `achievements`, политики доступа RLS и функции начисления баллов.

## 2. Аккаунт учителя

На сайте учитель входит с логином **`teacher`** и своим паролем. Личная почта и подтверждение по письму не нужны. Для встроенной авторизации Supabase логин преобразуется во внутренний адрес. Этот адрес не является почтовым ящиком и не показывается пользователям сайта.

В Supabase откройте **Authentication → Users → Add user → Create new user**. В поле Email вставьте этот технический идентификатор:

```text
t-1057a9604e04b274da5a4de0c8f4b4868d9b230989f8c8c6@teachers.management-laboratory.invalid
```

Задайте новый сложный пароль минимум из 8 символов. Включите **Auto Confirm User**. Пароль сохраните у себя: передавать его разработчику не нужно. Старый демонстрационный пароль больше не используется.

В SQL Editor выполните файл **`supabase/setup-teacher.sql`**. В результате должна появиться **одна строка**. Если строк нет, проверьте, что пользователь создан именно с указанным техническим идентификатором. Для другого логина нужен другой идентификатор — его вычисляет `teacherEmail` в `src/lib/student-identity.ts`; обычная замена текста `teacher` в форме создания аккаунта не подойдёт.

В **Authentication → Sign In / Providers** отключите **Allow new users to sign up**. Email/password должен оставаться включённым. Административная функция продолжит создавать учеников. Роль учителя назначается только записью в `teachers` через доверенный SQL Editor, а не метаданными пользователя.

## 3. Функция управления учениками

Функция позволяет создавать аккаунты учеников, задавать новые пароли и удалять их без раскрытия административного ключа в браузере.

1. Откройте **Edge Functions → Deploy a new function → Via Editor**.
2. Назовите функцию **`manage-students`**.
3. Вставьте код из `supabase/functions/manage-students/index.ts` вместо примера и опубликуйте.
4. В настройках функции отключите **Verify JWT with legacy secret** / **Enforce JWT verification**, если включено. Проверка JWT выполняется внутри функции через `auth.getUser`, затем обязательно проверяется запись в `teachers`. Это поддерживает новые ключи подписи Supabase.

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` предоставляются серверной функции автоматически. Не копируйте административный ключ в сайт. Не удаляйте проверки `auth.getUser` и `teachers`.

Альтернатива — официальный CLI из папки проекта:

```bash
npx supabase login
npx supabase functions deploy manage-students --project-ref pnpanexhudlalavcevck
```

Настройка проверки токена указана в `supabase/config.toml`. Все административные действия внутри функции требуют действующего пользовательского JWT и роли учителя. Одного Publishable key недостаточно.

## 4. Публикация и проверка

После шагов 1–3 отправьте новую версию на GitHub и дождитесь успешного **Deploy GitHub Pages**.

1. Войдите в кабинет учителя с логином **`teacher`** и новым паролем. Технический адрес вводить на сайте не нужно.
2. Добавьте `Тестовый Ученик | пробный-пароль-123`.
3. На другом устройстве без VPN войдите как ученик по ФИО и этому паролю.
4. Выдайте баллы и ачивку из кабинета учителя. Данные ученика обновляются при возврате во вкладку и каждые 15 секунд, пока она открыта.
5. Ученик видит только свои данные и своё место; полный класс доступен учителю.
6. После проверки удалите тестового ученика из кабинета учителя.

## Старые данные

В том же браузере и на том же домене, где раньше велись баллы, войдите в новый кабинет учителя и нажмите **«Перенести учеников с этого устройства»**. Переносятся ФИО, баллы, ачивки — до 30 учеников за раз. Совпадения по ФИО пропускаются с сообщением; существующие записи базы не перезаписываются.

Короткие старые пароли заменяются случайными. Данные входа показываются после создания аккаунтов: сохраните их и передайте каждому ученику только его пароль. После ухода со страницы прочитать сохранённые пароли нельзя, но учитель может задать новые. Исходное локальное хранилище не очищается автоматически.

Если данные остались на localhost, выполните перенос с локально запущенной новой версией (`npm run dev`) в том же браузере — она использует ту же общую базу.

## Проверки и ограничения

```bash
npm ci
npm run lint
npm run typecheck
npm test
GITHUB_PAGES=true npm run build
```

Тесты применяют реальную SQL-миграцию к PostgreSQL в памяти и проверяют права анонимного пользователя, ученика, учителя, запрет повышения роли, начисления, импорт и каскадное удаление. Отдельные тесты проверяют авторизацию Edge Function, согласованность ФИО при входе и откат незавершённого создания аккаунта. После настройки необходимо отдельно проверить живой проект.

Проект рассчитан на один общий класс. ФИО уникальны; для полных тёзок добавьте различающий суффикс и используйте его при входе. Пароли — от 8 до 128 символов. При равных баллах рейтинг упорядочен по ФИО и ID в PostgreSQL.

При ошибке сети сайт показывает ошибку и не записывает изменения в отдельную локальную копию. При пакетном добавлении показываются успешные записи и ошибки по остальным. Массовое удаление выполняется последовательно: при ошибке часть учеников уже может быть удалена, обновите список перед повтором. Бесплатный Supabase может приостанавливаться после недели неактивности.

Официальные инструкции: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [создание пользователей](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [Edge Functions через панель](https://supabase.com/docs/guides/functions/quickstart-dashboard).


## Обновление от 6 ноября: администраторы из учеников

1. В SQL Editor выполните **весь** файл `supabase/migrations/202611060001_student_administrators.sql`. Повторное выполнение допустимо; существующие ученики и результаты сохраняются.
2. В Edge Functions откройте `manage-students`, замените код содержимым `supabase/functions/manage-students/index.ts` и нажмите **Deploy updates**. `Verify JWT with legacy secret` остаётся выключенным: функция сама проверяет пользователя через `auth.getUser`.
3. В новом кабинете преподавателя откройте **Администраторы → Назначить**, выберите существующего ученика. Отдельный логин и пароль не создаются. Администратор входит через **Администратор** с теми же данными, а личный дневник остаётся доступен.

По умолчанию администратор добавляет учеников, пока в классе меньше 26 участников, удаляет до 5 учеников в день, изменяет баллы на общую абсолютную сумму до 100 в день и выдаёт до 10 новых наград в день. Удаление освобождает место. Дневные лимиты сбрасываются по московскому календарю в 00:00. Массовое начисление 10 баллов пяти ученикам расходует 50. Повторная выдача уже существующей награды не расходует лимит. Преподаватель может изменить эти ограничения; ноль запрещает действие.

Администратор не меняет пароли, свои результаты и результаты других администраторов, не удаляет себя/других администраторов и не назначает права. Преподаватель снимает права без удаления ученика и его результатов. Снятие и повторное назначение в тот же день не обнуляют расход. Операции, лимиты и журнал фиксируются транзакционно в PostgreSQL. Удаление учётной записи выполняется внутри серверной SQL-функции; при ошибке связанных записей операция целиком откатывается. В приложении нет пользовательских Storage-объектов.

### Просмотр паролей

Только преподавателю доступна кнопка **Ученики → Доступ → Посмотреть пароль**. Старые пароли, созданные до обновления функции, восстановить из Supabase Auth нельзя. После создания ученика или задания нового пароля копия шифруется AES-GCM на сервере и сохраняется в `student_credentials`. Роли `anon` и `authenticated`, включая преподавателя, не имеют прямого доступа к этой таблице. Расшифрование выполняет только Edge Function после проверки роли преподавателя; ответ имеет `Cache-Control: no-store`. Пароль показывается на 30 секунд и очищается при закрытии строки. В localStorage пароли не сохраняются.

Ключ шифрования выводится из серверного `SUPABASE_SERVICE_ROLE_KEY` с отдельным контекстом. Этот ключ не передаётся в браузер. При его ротации старые копии потребуют перешифрования или задания новых паролей. Пароли в Supabase Auth продолжают храниться в виде хеша.

### Проверка после обновления

Назначьте реального ученика администратором. Убедитесь, что он входит по прежним данным, видит личный дневник, а служебный кабинет показывает ограничения 26 / 5 / 100 / 10. Выдайте обычному ученику 1 балл и проверьте расход и запись в журнале. Не используйте реальные удаления для проверки дневного лимита: лимит и атомарный откат покрыты локальными тестами. Старые отдельные аккаунты администраторов из прежней версии автоматически не получают эти новые права — преподаватель назначает их существующим ученикам.

## Эмодзи-чаты учеников

В SQL Editor выполните **весь** файл `supabase/migrations/202611060002_emoji_chats.sql`. Он применяется после основных таблиц класса; повторное выполнение допустимо. Edge Function `manage-students` менять для чатов не нужно.

Ученик открывает **Мой дневник → Чаты**, выбирает одноклассника и отправляет один из восьми эмодзи. История сохраняется в базе. Ученик-администратор тоже может пользоваться чатами как ученик. Преподаватель исключён из отправителей, получателей и доступа к перепискам, даже если для его ID существует ученический профиль. Список собеседников содержит имена и метаданные только собственных разговоров, без чужих баллов, паролей и адресов авторизации.

Прямые записи в таблицы чатов запрещены для клиентских ролей. Серверные RPC проверяют участника, выбранный эмодзи и блокировки. Таблицу сообщений читают только два участника конкретного диалога; права администратора класса не открывают чужую переписку. Прочитанные позиции и список блокировок видны только владельцу. Повтор запроса после потери связи использует прежний `client_nonce` и не создаёт второе сообщение.

Ограничение частоты: один новый эмодзи не чаще 600 мс, до 30 в минуту и 500 в день по московскому календарю. Блокировка останавливает отправку в обе стороны, а старую историю не удаляет. При удалении ученика его сообщения и связанные настройки удаляются каскадно.

Миграция включает таблицу сообщений в `supabase_realtime`, если такая публикация существует. В браузере подписка служит сигналом обновления; на случай разрыва WebSocket есть опрос раз в 3 секунды, только пока вкладка видима. Старые сообщения при открытии сайта не запускают повторные анимации. Непрочитанные при этом сохраняются.

В настройках чатов можно выключить анимации. Звук полностью удалён. Пароли и переписки в localStorage не сохраняются; там остаётся только переключатель эффектов. Старое сохранённое значение звука игнорируется.

При открытии диалога все непрочитанные эмодзи запускаются в порядке отправки с интервалом 300 мс, каждый отдельной анимацией, даже если они получены до входа на сайт. Эффекты накладываются друг на друга, каждый сохраняет около четырёх секунд разлёта. Поле ввода доступно во время показа. Эмодзи отмечается прочитанным после завершения своего эффекта. Закрытие чата или скрытие вкладки приостанавливает очередь; оставшиеся эмодзи сохраняются непрочитанными и продолжаются при возврате. Уже просмотренная история не проигрывается. В открытом видимом диалоге новые эмодзи показываются сразу. Если диалог закрыт, появляется уведомление, а эффект ждёт его открытия. Текстовые сообщения не запускают эффект. Разлёт 48 крупных символов длится около четырёх секунд и занимает весь экран. При включённом системном уменьшении движения анимация отключена.

Живую проверку проведите с двумя ученическими аккаунтами на разных устройствах: отправьте эмодзи при закрытом диалоге или до входа получателя, откройте диалог и проверьте разлёт, отправьте 22 разных или одинаковых эмодзи — должно быть 22 отдельных эффекта, запускаемых каждые 0,3 секунды с наложением. Закройте чат после нескольких эффектов и откройте снова: оставшаяся очередь должна продолжиться. Полностью просмотренные эффекты не повторяются. Проверьте живое получение и блокировку. Не используйте аккаунт преподавателя в качестве получателя.

## Домашние задания и текстовые сообщения

После миграции эмодзи-чатов выполните **весь** файл `supabase/migrations/202611060003_homework_messages.sql` в новом запросе SQL Editor. Миграция аддитивная и допускает повторный запуск. Edge Function `manage-students` менять не требуется.

- Преподаватель и назначенные администраторы публикуют и редактируют ДЗ, задают необязательную дату сдачи и отправляют выполненные задания в архив. Можно вернуть задание из архива. Записи об этих действиях идут в журнал.
- Ученики видят актуальные задания перед результатами в своём дневнике. Доступ получают только участники класса; анонимам и посторонним аккаунтам чтение закрыто. Прямые записи в таблицу из браузера запрещены, публикация проверяет роль на сервере.
- Редактирование использует номер версии: устаревшая форма не перезаписывает более свежие изменения другого сотрудника. Повтор первой публикации с тем же ID не создаёт вторую запись.
- Текстовые сообщения до 2000 символов используют ту же историю и непрочитанные, что и эмодзи. Преподаватель не участвует в переписке; администратор видит только собственные диалоги. Блокировка действует на текст и эмодзи в обе стороны.
- Общие ограничения чатов сохранены: 600 мс между отправками, до 30 сообщений в минуту и 500 в день (Москва). Уникальный ID запроса предотвращает дубли при повторе отправки. Текст отображается как текст, без HTML или Markdown.
- На компьютере Enter отправляет текст, Shift+Enter добавляет строку. На телефоне Enter добавляет строку, сообщение отправляется кнопкой. Черновики отдельных диалогов хранятся только в памяти открытой вкладки.
- Обновление ДЗ: Realtime, при его недоступности — раз в 15 секунд в видимой вкладке и при возврате к ней. Чаты сохраняют существующую синхронизацию.

Проверка после SQL: войдите преподавателем, откройте «Домашние задания», опубликуйте задание и проверьте его в ученическом аккаунте. Измените задание из кабинета администратора, затем уберите в архив и верните. В двух ученических аккаунтах отправьте текст и эмодзи, проверьте повторный вход и блокировку.

## Классный журнал и посещаемость

После предыдущих миграций выполните весь `supabase/migrations/202611070001_attendance.sql` в новом запросе SQL Editor. Повторный запуск допустим. Обновление Edge Function не требуется.

В кабинетах преподавателя и администратора появился раздел «Классный журнал». Прежний журнал операций называется «История действий».

- Месяц выбирается над таблицей. Строки — ученики, столбцы — созданные занятия. На телефоне таблица прокручивается по горизонтали; имена и заголовки закреплены.
- «Добавить занятие» предлагает четверг выбранного месяца и позволяет указать другую дату. «Добавить занятия на четверги» создаёт четверги месяца без дублей. Уже отменённая дата от повторного добавления не восстанавливается.
- Нажатие на ячейку открывает меню отметки: П — присутствовал, Н — отсутствовал, О — опоздал, У — уважительная причина. «Без отметки» убирает запись статуса. Пустые ячейки не считаются отсутствием.
- Выбранная дата имеет сводку и кнопку массового присутствия: она затрагивает только текущих учеников без отметки, сохраняя выставленные пропуски и другие статусы. Поиск в таблице не сужает эту массовую операцию.
- Занятие можно отменить с необязательной причиной и восстановить. Отмена сохраняет отметки, запрещает их редактировать и исключает занятие из статистики.
- Посещаемость за месяц = (присутствовал + опоздал) / число непустых отметок в неотменённых занятиях. Если отметок нет, вместо процента показано тире.
- В журнале сохраняется снимок имени и идентификатор ученика. Удаление аккаунта из класса не стирает его историческую посещаемость. Исторические строки подписаны «Удалён из класса». Новому ученику можно поставить отметку в ранее созданном занятии.
- Читать и менять журнал могут только преподаватель и действующие администраторы. Ученики и посторонние не получают записи. Записи напрямую из браузера запрещены; RPC проверяют роль и версию. Устаревшая правка не перезапишет чужую; массовое сохранение атомарно. Отметки посещаемости не расходуют лимиты баллов или наград.
- Изменения дат, отмены и отметок попадают в «Историю действий». Realtime дополняется обновлением раз в 15 секунд в видимой вкладке и при возвращении к ней.

Проверка: создать четверги месяца, отметить одного ученика и затем остальных без отметки; поменять статус из другого сотруднического аккаунта; отменить и восстановить дату; проверить сохранность отметок после перезагрузки. Обычному ученику доступ к таблицам и RPC закрыт.

Порядок подключения, создание первого CSA по точному Auth UUID и настройки 2FA описаны в [SECURITY-SETUP.md](SECURITY-SETUP.md). Не публикуйте новый фронтенд до обновления серверной части.

## Удаление сообщений и замечания преподавателя

В SQL Editor выполните весь `supabase/migrations/202611070004_message_deletion_remarks.sql` после миграций безопасности и входа CSA. Повторный запуск безопасен; Edge Functions обновлять не нужно. Затем публикуйте обновлённый фронтенд.

Ученик может удалить своё текстовое сообщение или эмодзи у обоих собеседников. Текст и эмодзи очищаются, остаётся отметка «Сообщение удалено». Сохраняются идентификатор, время и nonce, поэтому удаление не позволяет обойти лимиты отправки или восстановить сообщение повтором запроса. Удаление синхронизируется отдельно от новых сообщений, отменяет ещё не просмотренные эффекты. Преподаватель и CSA не получают доступ к содержимому переписок.

Преподаватель и CSA отправляют замечания через раздел «Замечания», выбрав ученика и текст до 2000 символов. Обычный администратор не может отправлять замечания. Ученик видит постоянное уведомление с приглушённым красным фоном, текстом и кнопкой «Понятно» — таймера, закрытия по клику снаружи или Escape нет. Нажатие сохраняется в базе, закрытое замечание не возвращается после перезагрузки. Администратор, который остаётся учеником, также видит замечания в своём кабинете.

События отправки и закрытия замечаний, удаления своих сообщений записываются в журнал безопасности без текстов переписки и замечаний. Реальные права, приватность, повторные запросы и сохранение закрытия проверяются PostgreSQL-тестами.

## Материалы занятий и презентации

Выполните весь `supabase/migrations/202611120001_lesson_materials.sql` после предыдущих миграций. Повторный запуск допустим; Edge Functions менять не нужно. Запрос создаёт приватный Storage bucket `lesson-presentations` и таблицы материалов, не меняя существующие отметки посещаемости.

В кабинете преподавателя откройте «Занятия и материалы». Выберите дату из журнала или добавьте новую: укажите тему, что прошли, презентации и ДЗ с необязательным сроком. До 10 презентаций на занятие: файлы PDF/PPTX до 25 МБ каждый или HTTPS-ссылки. Снимите «Показывать ученикам», чтобы сохранить черновик. Публиковать и редактировать могут преподаватель и CSA; администраторы из учеников могут только читать опубликованные материалы в своём дневнике.

У ученика раздел «Занятия» показывает опубликованные уроки выбранного месяца. Нажатие на занятие открывает описание, презентации и затем ДЗ. PDF открывается внутри занятия с запасной ссылкой в новую вкладку, PPTX скачивается для PowerPoint/Keynote. Прикреплённые ссылки открываются отдельно. Общее ДЗ в дневнике продолжает работать независимо.

Файлы закрыты от посторонних и анонимов; для просмотра выдаётся ссылка на 5 минут. Удаление презентации из формы применяется после сохранения. Сервер запрещает удалять файлы, пока они прикреплены к занятию, проверяет версию материалов и записывает изменения в журнал безопасности. Список обновляется раз в 30 секунд в видимой вкладке и при возвращении к ней.

Проверка: опубликуйте занятие с двумя презентациями и ДЗ, откройте его в ученическом аккаунте, затем отредактируйте и сохраните черновиком. Проверьте, что у ученика оно скрыто, а отметки в классном журнале сохранены.
