# Безопасность и CSA: подключение

Код проверяется локально. Эта инструкция сама по себе не меняет Supabase. Примените обновление в следующем порядке, затем публикуйте новую версию сайта. На время обновления операции с аккаунтами могут возвращать «Проверка безопасности недоступна»; это намеренный отказ при отсутствии проверки.

1. **Edge Functions → manage-students:** заменить код всем содержимым `supabase/functions/manage-students/index.ts`, Deploy updates. JWT gateway verification оставить выключенной, как в `supabase/config.toml`: функция сама проверяет пользователя через Auth и его действующую сессию/2FA через БД. Никогда не убирать эти проверки.
2. **Edge Functions → Create function → security-admin:** создать функцию с этим точным именем, вставить `supabase/functions/security-admin/index.ts`, Deploy; JWT gateway verification также выключена. `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` — стандартные серверные переменные Supabase. Service key не добавлять в сайт, GitHub или чат.
3. **SQL Editor → New query:** выполнить весь `supabase/migrations/202611070002_security_csa.sql`. Повторный запуск безопасен. Миграция опирается на уже применённые миграции класса, администраторов, чатов, ДЗ и посещаемости. Пользователи, результаты и переписки сохраняются. Старые сервисные RPC создания/удаления учеников закрываются; поэтому обновить Edge из шага 1 обязательно.
4. После успешного выполнения можно публиковать фронтенд. У преподавателя появляется **Безопасность**: события, устройства и настройка 2FA. У обычного администратора этого раздела нет.

## Первый CSA

1. Authentication → Users → Add user: адрес **csa@csa.management-laboratory.invalid**, подтверждённый пользователь (Auto Confirm User). Придумайте уникальный пароль от 12 символов и сохраните в менеджере паролей. Не присылайте пароль в чат.
2. Скопируйте UUID именно этого пользователя.
3. Откройте `supabase/setup-csa.sql`, замените `REPLACE_WITH_EXACT_AUTH_USER_UUID` на UUID. Выполните весь файл в SQL Editor. Скрипт одновременно проверяет UUID, адрес и отсутствие другого CSA; самостоятельно зарегистрированный пользователь прав не получит.
4. На сайте выберите **CSA** и войдите с логином **csa**. Затем настройте приложение-аутентификатор и подтвердите шестизначный код. Пока 2FA не подтверждена, кабинет и привилегированные запросы закрыты.
5. Новых преподавателей и CSA создавайте через **Безопасность → Аккаунты**. Преподаватель может назначать обычных администраторов из учеников, но не CSA.

Технические адреса выше — внутренние идентификаторы для логина; настоящий почтовый ящик не требуется. Пароли преподавателей и CSA можно заменить, но нельзя прочитать. Ранее запрошенный просмотр сохранённых паролей учеников остаётся только у преподавателя/CSA и теперь записывается в журнал.

## Настройки Auth у владельца проекта

- В Authentication → Sign In / Providers отключите публичную регистрацию (**Allow new users to sign up**). Пользователей создают серверные функции через Admin API.
- Убедитесь, что TOTP MFA разрешена. Настройте её у преподавателя через **Безопасность → 2FA**. Пароль, известный постороннему, перестанет быть достаточным для нового входа после включения 2FA.
- В настройках Email/Password задайте минимальную длину пароля хотя бы 8 символов. Сервер дополнительно требует 12 для сотрудников и CSA. Если ваш тариф поддерживает проверку скомпрометированных паролей, включите её.
- Сохраните ограничения частоты входов/проверки MFA в Auth → Rate Limits. Защита входа работает на стороне Supabase; фронтенд не может заменить серверное ограничение запросов.
- Сохраните TOTP-ключ в защищённом менеджере. CSA не может сбросить собственную 2FA из своей сессии. При потере доступа восстановление выполняет владелец Supabase через Authentication → Users; после удаления фактора старые сессии отзываются, новый вход потребует настройки 2FA заново. Пароль/роль CSA не создаются автоматически из настроек браузера.

[Документация MFA](https://supabase.com/docs/guides/auth/auth-mfa), [ограничения запросов](https://supabase.com/docs/guides/auth/rate-limits), [безопасность паролей](https://supabase.com/docs/guides/auth/password-security).

## Что проверять после подключения

- Преподаватель выдаёт баллы → в событиях видны исполнитель, получатель, изменение баланса и сессия. Администратор не может открыть этот журнал даже прямым RPC-запросом.
- Вход с нового браузера → одна запись успешного подтверждённого входа. Обновления страниц и клики не создают события.
- CSA завершает чужую сессию → прежний access token не может читать таблицы или выполнять действия. Список устройств отражает реальные Auth-сессии, а не браузерный localStorage.
- CSA меняет пароль преподавателя → старые сессии теряют доступ, новый пароль работает. Смена через сам Auth тоже создаёт событие. Пароли, хеши и одноразовые коды в события не попадают.
- CSA меняет эмодзи → новые изображения появляются в панели, истории и анимациях чатов при ближайшем обновлении (до 15 секунд). Преподаватель не становится участником личных переписок.

Журнал начинает фиксировать события после миграции. Он защищён от редактирования всеми ролями приложения, включая CSA; владелец базы и service key остаются доверенными. Браузер/IP описывают сессию и не доказывают личность. Уже загруженные на чужое устройство данные нельзя стереть удалённо.

Сборка добавляет в статические HTML Content Security Policy с хешами разрешённых inline-скриптов, запрещает обработчики `onclick` из HTML и подключения к посторонним API. GitHub Pages не позволяет задать произвольные HTTP-заголовки: для HSTS, `frame-ancestors` и полноценного серверного контроля заголовков нужен подходящий хостинг/прокси. Не вставляйте фиктивные CSP-заголовки в настройки клиента Supabase.
